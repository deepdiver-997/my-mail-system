# 邮件协议流程入门（SMTP / IMAP / POP3）

> 面向不熟悉邮件协议的人。三页纸讲清"发信、收信、读信"各是哪个协议干的、
> 会话怎么流转、以及为什么多客户端并发会出问题。看懂这篇再读
> [架构文档](README.md) 和 [并发对照](architecture/mailbox-concurrency.md)。

## 一句话定位

| 协议 | 干什么 | 角色 | 类比 |
|------|--------|------|------|
| **SMTP** | **发**信（投递到对方服务器） | 送信人 | 把信塞进邮筒，邮局负责送达 |
| **IMAP** | **读**信（邮件留在服务器上，多设备同步） | 邮箱主人 | 邮箱放在邮局，随时翻开看 |
| **POP3** | **下载**信（下载后通常本地删除） | 取信人 | 把邮箱整个搬回家 |

三个协议解决不同问题，所以状态机、响应格式、并发策略都不一样。

## 先记三个贯穿的概念

1. **状态机**：每个连接都是一个状态机，服务器只在特定状态接受特定命令。
   比如 POP3 没登录前不能 STAT，IMAP 没选邮箱不能 FETCH。
2. **响应格式**：SMTP 用数字码（`220`/`250`/`354`），IMAP 用 tag（`A001 OK ...`），
   POP3 用 `+OK`/`-ERR`。多行数据（邮件正文、能力列表）都以一个特殊行结束。
3. **消息标识**：怎么指认"第几封信"？两种方式——
   - **位置号**（第 1 封、第 2 封…）：简单，但**删一封后面的就前移** → 并发时身份漂移
   - **UID**（唯一 ID）：稳定，删了也不变 → 并发安全
   IMAP 用 UID（= 本项目的 snowflake mail_id），POP3 用位置号。**这就是并发问题的根源**。

## SMTP — 发信

一次会话 = 送一封信（或一批），发完即走：

```
客户端                     服务器
  │  ──连接──▶   220 欢迎
  │  EHLO          250-能力列表（多行）
  │  MAIL FROM:<a>  250 发件人 OK
  │  RCPT TO:<b>    250 收件人 OK      ← 可多个收件人
  │  DATA           354 开始发正文
  │  <正文...>      250 收到
  │  QUIT           221 再见
```

要点：**会话短、无长生命周期状态**。DATA 之后服务器落盘（`mails` + `mail_mailbox`
插入新行）。因为是"插入新行"而非"改别人正在读的行"，并发投递天然安全。

## IMAP — 读信（多会话）

```
客户端                     服务器
  │  ──连接──▶   * OK 欢迎
  │  A001 LOGIN     A001 OK 登录成功
  │  A002 LIST "" *  A002 OK (INBOX "Sent" ...)
  │  A003 SELECT INBOX  * 5 EXISTS / * OK [UIDNEXT 6]
  │  A004 FETCH 1:5 (FLAGS)  * 1 FETCH ...（可多行）
  │  A005 STORE 1 +FLAGS (\Deleted)  A005 OK
  │  A006 EXPUNGE    * 1 EXPUNGE
  │  A007 LOGOUT    * BYE / A007 OK
```

要点：
- **允许多个会话同时读同一个邮箱**（手机、电脑各连一个）。
- 每条命令带 **tag**（`A001`），服务器回复时带回，客户端能对上号。
- 消息用**序号或 UID** 指认。序号是 1..N 的位置；UID 是稳定 ID。
- 每次 FETCH **重新查数据库**，不缓存冻结快照 → 别的会话删了信，这边查不到了（正确行为）。
- 并发隐患在 **UIDNEXT**（"下一条新邮件的 UID 是多少"）——已修，见
  [mailbox-concurrency.md](architecture/mailbox-concurrency.md)。

## POP3 — 取信（单会话）

```
客户端                     服务器
  │  ──连接──▶   +OK 欢迎
  │  CAPA           +OK 能力列表（多行，以 . 结束）
  │  USER alice     +OK 发密码
  │  PASS xxx       +OK 已锁定邮箱，2 封邮件（43 字节）
  │  STAT           +OK 2 43
  │  LIST           +OK 清单（多行，以 . 结束）
  │  RETR 1         +OK 正文（以 . 结束，行首 . 需转义）
  │  DELE 1         +OK 标记删除（不立即删！）
  │  QUIT           +OK 再见（此时才真正删）
```

要点：
- 比 IMAP 简单得多：**固定收件箱、无多邮箱概念**。
- 消息用**位置号**（1..N）指认。
- **DELE 只是标记，QUIT 才提交删除** → 会话期间必须有"只有我在操作"的保证，
  否则两个会话互相看对方删信，位置号就乱了。
- 所以 RFC 1939 §6 要求**单会话锁定**：一个用户同一时间只允许一个 POP3 会话，
  第二个会话直接拒绝（`-ERR [IN-USE]`）。
- 本项目的锁做成了带心跳的租约（防会话崩溃后锁泄漏死锁），见
  [pop3-server-design.md](architecture/pop3-server-design.md) 的「锁 → 租约」节。

## 为什么之前会有并发问题（速览）

不熟悉协议的人最容易困惑的其实是这里——三个协议面对"多客户端同时操作邮箱"
用了**完全不同的策略**，不是设计不一致，而是协议定位不同：

| | 标识方式 | 并发策略 | 为什么 |
|---|---------|---------|--------|
| SMTP | 无（只投递） | 靠 DB 行锁（插入新行） | 会话短、只写不读、无共享状态 |
| POP3 | 位置号 | **单会话锁**（排他） | 位置号身份依赖"只有我在改" |
| IMAP | UID | **无锁 + 每次查库** | 多设备必须并存，靠稳定 UID 兜 |

详细分析（含三层心智模型）见 [mailbox-concurrency.md](architecture/mailbox-concurrency.md)。
